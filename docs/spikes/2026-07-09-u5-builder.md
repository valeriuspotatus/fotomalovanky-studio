# U5 spike — builder integration (resolved: Playwright + headless print)

**Date:** 2026-07-09
**Unit:** U5 (`BuilderDriver`), resolves the Phase-0 builder seam.
**Verdict:** **Drive the existing builder with Playwright and render via headless Chromium's
print pipeline (`page.pdf()`).** The fallback A4-layout re-implementation is **not needed** —
`page.pdf()` reproduces the builder's own print output exactly. No HTTP API to script (the
builder is entirely client-side), so browser automation is the mechanism, as KTD3 anticipated.

## How this was determined

Read-only fetch of the builder app and its assets (no upload, no PDF generated):
`GET /` (`builder.html`), `GET /app.js`, `GET /collage-layout/collage-layout.js`, `GET /styles.css`.

## What the builder is

A static client-side single-page app ("A4 Gallery Builder"). No backend involved in the
folder→PDF flow. Key mechanics from `app.js` / `styles.css`:

- **Folder load:** one input — `<input type="file" id="folderInput" webkitdirectory directory multiple accept="image/*,.svg">`.
  `handleFolderSelect` groups files by base name.
- **Pairing rules** (`groupFilesByBaseName`): it pairs a **photo (`.jpg`/`.jpeg`) with an SVG**,
  and **explicitly skips `_bw.png`** (`if (name.endsWith('_bw.png')) continue`). The SVG may be
  named `<base>.svg` or `<base>_bw.svg` (both accepted). **Our generator's `<base>.svg` fits.**
  → The builder's real input contract is **`<base>.jpg` + `<base>.svg`**; the `_bw.png` is *not*
  used by the builder (it stays useful for the U4 QC heuristic / operator preview only).
- **Export:** `printBtn.addEventListener('click', () => window.print())`. **No PDF library** —
  the PDF is produced by the browser under `@media print { @page { size: A4 portrait; margin: 0 } … }`,
  which hides the UI chrome and lays out each page as an isolated A4 block.
- **Controls** (IDs the driver uses): `#titleInput` (dedication textarea), mode buttons
  `.mode-btn[data-mode="gallery"|"fullpage"]`, `#rotationMin` / `#rotationMax`, `#printPdfMode`
  (checkbox, default on), `#addAllCoverBtn` + `#coverSelection` (cover page), `#coverScale`,
  `#printBtn` (enabled only once ≥1 pair loads).
- **Images** load as `<img>` from `URL.createObjectURL(...)` — asynchronous, so the driver must
  wait for them before printing.

## Driver design (`src/builder/builderDriver.js`)

`buildPdf(orderDir, options)`:
1. `collectPairs(orderDir)` — find `<base>.jpg/.jpeg` + `<base>.svg`; error clearly if none.
2. Launch headless Chromium (Playwright), open the builder URL.
3. `setInputFiles('#folderInput', [photo, svg, …])` — pairing keys off `file.name`, so
   `webkitRelativePath` being empty under automation doesn't matter (folder name is cosmetic).
4. Wait for `#printBtn:not([disabled])` (= pairs loaded), then apply options (title/dedication,
   mode, rotation, optional "add all covers"). Controls are set on screen — the driver does **not**
   emulate print media here, since the print stylesheet hides these controls.
5. Wait until every `#pagesContainer img` is `complete && naturalWidth > 0`, plus a short settle.
6. `page.pdf({ preferCSSPageSize: true, printBackground: true })` — Playwright's `page.pdf()` uses
   **print** media by default, so `@media print` + `@page A4` apply automatically. This is the
   builder's exact print output, minus the print dialog.
7. Validate `%PDF` header + non-zero size.

Typed `BuilderError` (`seam: 'builder'`, `step`) surfaces plain-language failures naming where it
broke (load / launch / render / export), per the plan's fail-loud requirement.

## Corrections to the plan's assumptions

- The builder pair is **`<base>.jpg` + `<base>.svg`**, not `<base>.jpg` + `<base>_bw.svg`. It
  *accepts* a `_bw.svg` name too, but our generator emits `<base>.svg`, which is fine.
- The **`_bw.png` is not a builder input** — the builder ignores it. (It's still worth keeping for
  QC/preview.) So U5 needs only the jpg+svg of the triple.

## Notable extra: a latent server integration

`app.js` has a `/session/{id}` path that loads pairs from `GET /api/session/{id}` +
`/api/session/{id}/files/{name}`. This implies the builder can be fed directly from a server-side
session (a possible future generator→builder hand-off that skips local files entirely). Out of
scope now, but recorded as a future de-risk option.

## Live validation (2026-07-09)

Ran `BuilderDriver.buildPdf` against the real 8-pair order 1522 folder (after
`npx playwright install chromium`). **The seam works:** it produced a genuine
`%PDF-1.4`, **A4-portrait** PDF (MediaBox 594.96 × 841.92 pt — matches the operator's
595.32 × 841.92) from all 8 photo+SVG pairs.

One `setInputFiles` gotcha fixed en route: a `webkitdirectory` input requires a **directory
path**, not a file array — the driver now passes `resolve(orderDir)`.

## Auto-tuned to match the operator's output (2026-07-09)

First run scored 20 pages vs the operator's 12 — but that was the **wrong input**: I built the
8-photo `1523` zip from the repo, while `1522 Final.pdf` was made from the **4-photo** finished
Desktop folder. Reading the builder's layout code gives the exact page-count formula for
`gallery` + `printPdfMode` (default on) + a title page present:

```
pages = 1 (title) + 1 (empty) + N×2 (each pair + empty) + 1 (empty) + 1 (last)
      = 2N + 4     →  N=4 ⇒ 12,  N=8 ⇒ 20
```

So the operator's routine is **gallery mode + Print-PDF on + a title page** (a title page renders
when there's *either* dedication text *or* selected cover images). Rebuilding the correct 4-pair
folder confirmed it:

| Config | pages | A4 | size |
|---|---|---|---|
| ours, gallery + `addAllCovers` | 12 | ✓ | 15.6 MB |
| **ours, gallery + title text only** | **12** | ✓ | **10.4 MB** |
| operator `1522 Final.pdf` | 12 | ✓ | 7.1 MB |

**Page structure matches exactly.** Title-only (no cover images) is closer on size, suggesting the
operator's title page is a dedication text, not a cover collage. The residual ~3 MB is Chromium's
print embedding/compression of the same SVGs+JPEGs, not a layout difference. Confirmed driver
defaults: `mode: 'gallery'`, Print-PDF left on, `title` per order, `addAllCovers` off by default.

## Live end-to-end confirmation (2026-07-09, U6)

Two real orders were driven all the way to PDF by `npm run go` against the live builder, and the
page-count formula was confirmed **by observation**, not just by reading the layout code:

| order | dedication | pages | formula |
|---|---|---|---|
| 1523 | *(none)* | 4 | `2N+2`, N=1 — **no title page** |
| 1510 | `Pro Barču, s láskou od rodiny` | 6 | `2N+4`, N=1 — title page present |

This settles the open item below: the title page is **not** optional decoration — its absence
silently prints a book two pages shorter than the operator's current output. So the dedication is
an order-level field, collected in the review grid, stored in `state.json`, and the run report
warns when an order has none. The Czech diacritics render correctly through `page.fill('#titleInput')`.
